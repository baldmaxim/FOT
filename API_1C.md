# Инструкция: подключение из 1С к FOT Data API

Read-only публичный API для внешних систем. Управление ключами и whitelist таблиц/полей — через админ-вкладку «API-доступ» в FOT.

---

## 1. Базовый URL

- Прод (HTTPS): `https://fot.su10.ru/external/v1`
- Прод (HTTP): `http://fot.su10.ru/external/v1`

## 2. Аутентификация

В каждый запрос (кроме `/health`) добавить HTTP-заголовок:

```
Authorization: Bearer fot_<prefix>_<secret>
```

Полный токен выдаётся **один раз** при создании ключа и имеет вид `fot_<16 hex>_<48 hex>`. Если токен потерян — нужно создать новый ключ.

## 3. Доступные endpoints (только GET, read-only)

| Метод | URL | Назначение |
|---|---|---|
| GET | `/external/v1/health` | Проверка доступности (без авторизации) |
| GET | `/external/v1/tables` | Список таблиц, разрешённых ключу |
| GET | `/external/v1/tables/{name}/schema` | Список полей таблицы |
| GET | `/external/v1/tables/{name}` | Чтение строк таблицы |

## 4. Параметры query-string для чтения данных

- `limit` — 1..1000, по умолчанию 100
- `offset` — пропустить N строк, по умолчанию 0
- `order=поле.asc` или `order=поле.desc`
- Фильтры: `eq.поле=значение`, `neq.`, `gt.`, `gte.`, `lt.`, `lte.`, `like.`, `ilike.`, `in.поле=v1,v2,v3`

Поля в фильтрах должны быть в whitelist ключа, иначе 400.

## 5. Формат ответа

```json
{
  "data": [ { ... }, { ... } ],
  "limit": 100,
  "offset": 0
}
```

## 6. Лимиты и ошибки

- Rate limit per-key — настраивается на ключе (default 60 req/min). При превышении — `429 Too Many Requests`.
- `401` — нет/неверный/отозванный/просроченный ключ.
- `404` — таблица недоступна этому ключу.
- `400` — поле не в whitelist, кривые параметры.

## 7. Документация Swagger

`https://fot.su10.ru/external/v1/docs` — интерактивная документация со всеми endpoints.

```bsl

    Хост      = "fot.su10.ru";
    Порт      = 443;             // стандартный HTTPS-порт
    ApiKey    = "fot_XXXXXXXXXXXXXXXX_YYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYY"; // подставить выданный токен

    SSL = Новый ЗащищённоеСоединениеOpenSSL();
    Соединение = Новый HTTPСоединение(Хост, Порт, , , , 30, SSL);

    ПолныйПуть = "/external/v1/" + Путь;
    Если ПараметрыЗапроса <> Неопределено И ПараметрыЗапроса.Количество() > 0 Тогда
        ЧастиQS = Новый Массив;
        Для Каждого КЗ Из ПараметрыЗапроса Цикл
            ЧастиQS.Добавить(КЗ.Ключ + "=" + Строка(КЗ.Значение));
        КонецЦикла;

    Запрос = Новый HTTPЗапрос(ПолныйПуть, Заголовки);
    Ответ  = Соединение.Получить(Запрос);

    Результат = Новый Структура("Код, Тело");
    Результат.Код  = Ответ.КодСостояния;

```

## Расчётный табель отдела (JSON)

Помимо «сырых» таблиц `/external/v1/*` есть **расчётный** эндпоинт: он отдаёт уже
собранный табель отдела со всеми корректировками (тот же расчёт, что в выгрузке
«Единый 1С»), а не сырые СКУД-события. Это отдельный путь на Node — `/api/public/v1`
(не `/external/v1`), но авторизация тем же data-api токеном.

- **URL:** `GET https://fot.su10.ru/api/public/v1/timesheet`
- **Авторизация:** `Authorization: Bearer fot_<prefix>_<secret>` (как обычно).
- **Требование:** ключу должна быть открыта таблица `employees` (вкладка «API-доступ» →
  ключ → «Таблицы»). Иначе `403`.

### Параметры query-string

| Параметр | Обязателен | Значение |
|---|---|---|
| `department_id` | да | UUID отдела/бригады. Несколько — через запятую. Поддерево НЕ раскрывается: подотделы перечисляйте явно. |
| `month` | да | Месяц `YYYY-MM`. |
| `half` | нет | `FULL` (по умолч.), `H1` (1–15), `H2` (16–конец). |
| `from`, `to` | нет | Произвольный диапазон `YYYY-MM-DD` внутри месяца (имеет приоритет над `half`). |

### Формат ответа

```json
{
  "period": { "month": "2026-06", "start": "2026-06-01", "end": "2026-06-30", "half": "FULL" },
  "departments": [
    {
      "id": "0e2c…uuid",
      "name": "бр. Иванова",
      "employees": [
        {
          "id": 123,
          "full_name": "Иванов Иван Иванович",
          "tab_number": "СУ10-000123",
          "sigur_employee_id": 4567,
          "position": "Маляр",
          "total_hours": 168,
          "days": {
            "2026-06-01": { "status": "work",    "hours": 8, "corrected": false, "hours_overridden": false },
            "2026-06-02": { "status": "vacation", "hours": 0, "corrected": true,  "hours_overridden": false }
          }
        }
      ]
    }
  ]
}
```

- `status` — машинный код дня, одно из одиннадцати значений: `work`, `manual`,
  `remote`, `vacation`, `sick`, `dayoff`, `unpaid`, `absent`, `educational_leave`,
  `sick_worked`, `study_day`. Значения `business_trip` и `study` удалены и больше
  не приходят.
- `hours` — часы за день. У неявок (`vacation`, `sick`, `dayoff`, `unpaid`,
  `absent`, `educational_leave`) здесь **норма планового графика**, а не
  отработанное время: переносить её как отработанную нельзя. Отработанные часы
  берутся у `work`, `manual` и `remote`; `sick_worked` и `study_day` засчитаны
  полным днём по норме. При `hours = 0` день не считается явкой ни при каком статусе.
- `corrected` — день получен/изменён ручной корректировкой; `hours_overridden` —
  часы заданы вручную поверх СКУД.
- `total_hours` — сумма часов за период.

### Ошибки

`401` — нет/неверный токен. `403` — ключу не открыта `employees`. `400` — нет/кривые
`department_id`/`month`/период.

### Проверка

```bash
curl -H "Authorization: Bearer fot_..." \
  "https://fot.su10.ru/api/public/v1/timesheet?department_id=<uuid>&month=2026-06&half=FULL"
```

# Закрытые согласованные табели — регулярный обмен с 1С

Раздел выше (`/api/public/v1/timesheet`) считает табель **на лету** за произвольный
период. Он остаётся рабочим, но для регулярной загрузки в 1С не подходит: по нему
нельзя понять, изменились ли данные с прошлого раза.

Ниже — основной механизм обмена. Машиночитаемый контракт — `docs/openapi-1c.yaml`
в репозитории проекта.

## 1. Что выгружается

Единица обмена — **подача табеля** (`approval_id`). Подачи бывают **двух видов**, и
различает их поле `scope.kind`:

| `scope.kind` | Что это | `department_id` | `manager_employee_id` |
|---|---|---|---|
| `department` | табель отдела или бригады | заполнен | пуст |
| `personal` | персональная подача руководителя «по людям» | **пуст** | заполнен |

**Обрабатывать нужно оба вида.** Персональных подач заметная доля — на момент
написания 257 из 866. Если 1С фильтрует выдачу по `kind = "department"` или
опирается на непустой `department_id`, эта часть табелей потеряется **молча**:
ошибки не будет, подачи просто не попадут в документы, а в ФОТ так и останутся
неподтверждёнными.

**Закрытый согласованный табель — неизменяемый официальный снимок.** В момент
утверждения и при каждом повторном закрытии ФОТ сохраняет версию: состав, часы по
дням, итоги. API отдаёт табель только из сохранённой версии и никогда не
пересчитывает его на лету. Из этого следуют три правила:

- фоновый пересчёт СКУД **не меняет** уже закрытый табель;
- чтобы правки попали в 1С, табель в ФОТ открывают, правят и закрывают заново;
- **новая редакция появляется только при согласовании и при закрытии.** Правок
  закрытого табеля «напрямую», в обход открытия, в ФОТ больше нет — они запрещены
  всем пользователям без исключения, включая администраторов.

**Пока табель открыт для правок, 1С продолжает получать последнюю закрытую редакцию.**
Подача не исчезает из выдачи, состояние не меняется, а незавершённые правки в API
не попадают физически: версия заморожена до закрытия.

## 1a. Глубина запроса и прямой доступ по идентификатору

**Список ограничен тремя месяцами.** `GET /timesheets` отдаёт подачи, у которых
`start_date` не раньше начала месяца, отстоящего на 3 месяца назад. Запрос глубже
возвращает `400` с текстом, где указана самая ранняя доступная дата.

Ограничение действует только у списка. **Метод по идентификатору глубиной не ограничен:**
`GET /timesheets/{approval_id}` отдаст табель в любой момент, сколько бы времени
ни прошло.

Практический вывод для 1С: **сохраняйте идентификатор подачи** `approval_id`
в своём документе. Тогда
пропущенный или отложенный период всегда можно догрузить точечно, даже когда он уже
вышел из окна списка. Искать его перебором списка будет поздно.

## 2. Состояния

| Состояние | Что значит |
|---|---|
| `not_exported` | Версия ещё не подтверждена — нужно забрать |
| `stale` | Принята более ранняя редакция, появилась новая — нужно забрать |
| `exported` | Последняя редакция принята, делать нечего |

Фильтр `needs_export=true` = `not_exported` + `stale`.

## 3. Жизненный цикл

| Событие в ФОТ | Что происходит внутри | Что видит 1С |
|---|---|---|
| Табель согласован | Создаётся версия 1 | `not_exported` |
| 1С загрузила и подтвердила | Записан ACK версии 1 | `exported` |
| Табель открыт для правок | Ставится `unlocked_at` | **Ничего не меняется:** версия 1 по-прежнему отдаётся и подтверждается |
| Внесены правки | Сохранённая версия 1 не меняется | Незакрытые правки недоступны |
| Закрыт **без** фактических изменений | Хэш совпал, новая редакция не создаётся | Остаётся `exported` |
| Закрыт **с** изменениями | Создаётся версия 2 | `stale`, попадает в `needs_export=true` |
| 1С загрузила версию 2 и подтвердила | Записан ACK версии 2 | Снова `exported` |
| Аварийное восстановление версии администратором БД | Версия помечается на пересборку и формируется заново | Табель временно не выдаётся (`TIMESHEET_REBUILD_PENDING`), потом — как при обычном закрытии |

Цикл повторяется без ограничений: каждое следующее закрытие с изменениями даёт
`revision` на единицу больше, и это всегда **одна и та же** подача (`approval_id`).
Повторное открытие не создаёт вторую запись и не возвращает прежние редакции как
отдельные табели.

## 4. Сопоставление сотрудников — реквизит `ID_FOT`

В ФОТ есть **полные однофамильцы** (57 групп, 114 человек), поэтому сопоставление
по ФИО недопустимо.

1. В справочнике «Сотрудники» 1С завести реквизит **`ID_FOT`** — целое число,
   уникальный индекс, доступен для поиска.
2. Один раз выполнить первичное сопоставление: выгрузить любой табель, сверить
   сотрудников по ФИО + подразделению и проставить `ID_FOT` = `identity.employee_id`.
   Спорные случаи (однофамильцы) развести вручную — их единицы.
3. Дальше сопоставление **только по `ID_FOT`**.

Остальные поля блока `identity`:
- `sigur_employee_id` — код в СКУД, резервный, для сверки;
- `tab_number` — **не ключ**: заполнен примерно у каждого восьмого и не уникален;
- `full_name` — только для отображения.

## 5. Какие строки переносить в документ

Ответ содержит **весь согласованный состав** — ровно тот, что был в закрытом табеле.
У каждого сотрудника есть флаг `zero_activity`:

- `zero_activity: false` — **переносить в документ**;
- `zero_activity: true` — за период нет ни одного реального сигнала (ни проходов,
  ни корректировок, ни объектной активности); такие строки в документ не переносятся.

Это соответствует прежнему правилу «не проходящие по СКУД не попадают в 1С».
Фильтра на стороне API нет намеренно: иначе `content_hash` и `employees_count`
не соответствовали бы фактически полученному телу.

## 6. Что должно быть настроено у ключа

Настраивает администратор ФОТ во вкладке «API-доступ», разработчику 1С делать ничего
не нужно — но если методы отвечают `403`, причина почти всегда здесь:

| Что | Где включается | Без него |
|---|---|---|
| Доступ к таблице `employees` | ключ → «Доступы» → отметить `employees` | `403` на всех методах табелей |
| Право подтверждать выгрузку | ключ → «Доступы» → «Разрешить подтверждение выгрузки табелей (POST /ack)» | `403` на подтверждении: табель заберётся, но останется в очереди навсегда |

В списке ключей колонка «Подтверждение 1С» показывает, включено ли право.

## 7. Порядок обмена

### Шаг 1. Узнать, что забирать

```
GET /api/public/v1/timesheets?month=2026-08&needs_export=true&limit=100
```

```json
{
  "period": { "month": "2026-08", "start": "2026-08-01", "end": "2026-08-15" },
  "data": [
    {
      "approval_id": 855,
      "scope": {
        "kind": "department",
        "department_id": "0e2c9f3a-1b4d-4c8e-9a10-2f3b4c5d6e7f",
        "department_name": "бр. Иванова",
        "manager_employee_id": null
      },
      "start_date": "2026-08-01",
      "end_date": "2026-08-15",
      "version_available": true,
      "revision": 2,
      "content_hash": "d41d8cd98f00b204e9800998ecf8427e",
      "employees_count": 28,
      "total_hours": 3248.5,
      "state": "stale",
      "last_export": { "revision": 1, "acked_at": "2026-08-16T06:03:11.000Z", "document_ref": "ТАБ-000123" }
    }
  ],
  "meta": { "without_version": 0 },
  "next_cursor": null
}
```

Метод лёгкий — табель не собирается, всё читается из сохранённых версий.
Опрашивать раз в минуту нормально.

**Пагинация — keyset.** Повторяйте запрос с `cursor` из `next_cursor`, пока тот не
станет `null`. Параметра `offset` нет: после подтверждения строки уходят из выборки
`needs_export=true`, и смещение пропускало бы сдвинувшиеся записи.

**`version_available: false`** — версия не сформирована, выгрузить нельзя: пропустить
строку и идти дальше. Это **штатная ситуация, а не сбой**. Счётчик
`meta.without_version` показывает, сколько таких в выборке.

Причина обычно одна: у подачи пустой состав — например, отдел расформировали ровно на
границе периода, и собирать версию не из чего. Такая подача останется без версии
навсегда, поэтому «повторить в следующем цикле» её не вылечит — просто пропускайте.
На момент написания такая подача одна из 866.

**Открытый для правок табель из списка НЕ пропадает.** Он отдаётся с последней
официально закрытой редакцией, и её можно как загрузить, так и подтвердить. Когда
табель закроют заново, появится следующая `revision`, состояние станет `stale`, и
подача сама вернётся в `needs_export=true`.

**Единственное исключение — аварийная пересборка версии.** В этом случае табель не
появляется в списке вообще (ни с фильтром, ни без), а `GET /timesheets/{id}` (в том
числе с явным `revision`) и `POST .../ack` отвечают `409 TIMESHEET_REBUILD_PENDING`:
содержимое версии меняется, и отдавать прежние часы нельзя. Ситуация редкая —
её вызывает только ручное восстановление данных администратором БД. Через ~минуту
табель вернётся в список уже с новой редакцией. Обработчик этого кода в 1С нужен,
но срабатывать он почти не будет.

Отработанные часы переносятся в документ только у `work`, `manual` и `remote`; у
`sick_worked` и `study_day` — по решению бухгалтерии. У остальных статусов в `hours`
лежит плановая норма дня, и запись её как отработанной даст оплату поверх отпускных и
пособий. При `hours = 0` день не считается явкой ни при каком статусе — нулевые часы
встречаются и у `work`, и у `manual`, и у `remote`.

Ветку «прочее» в обработчике лучше оставить с ошибкой: при появлении нового вида
времени табель не должен загрузиться молча и неверно.

### Шаг 2а. Забрать часы по объектам

Тело табеля отвечает «сколько часов в этот день», но не «на каком объекте». Там, где
учёт идёт по СКУД (например бригады «ЛИНИЯ» и «ЛИНИЯ-Общестрой»), день складывается из
проходов по нескольким объектам. Эта разбивка отдаётся отдельным методом,
**для той же редакции**:

```
GET /api/public/v1/timesheets/855/objects?revision=2
```

```json

  "scope": { "kind": "personal", "department_id": null, "manager_employee_id": 2617 },
  "start_date": "2026-08-01",
  "end_date": "2026-08-15",
  "revision": 2,
  "timesheet_content_hash": "d41d8cd98f00b204e9800998ecf8427e",
  "objects_content_hash": "9b74c9897bac770ffc029102a200c5de",
  "employees": [
    {
      "employee_id": 2617,
      "full_name": "Иванов Иван Иванович",
      "mode": "skud",
      "total_hours": 96.5,
      "objects": [
        { "object_id": "0e2c…", "object_name": "ЖК Примавера К14",
          "object_address": "г. Москва, …", "total_hours": 64,
          "days": { "2026-08-01": 8, "2026-08-03": 8 } },
        { "object_id": "7a11…", "object_name": "ЖК Ситибэй",
          "object_address": "г. Москва, …", "total_hours": 32.5,

  "meta": { "employees_count": 28 }
```

**Метод ничего не пересчитывает.** Разбивка заморожена вместе с редакцией: повторный
запрос той же `revision` вернёт те же данные и тот же `objects_content_hash`.

Правила:

- Запрашивать **с той же `revision`**, что забрали на шаге 2. Между двумя вызовами
  может появиться новая редакция.
- **Сумма часов по объектам за день совпадает с `days[дата].hours`** того же сотрудника
  из тела табеля **с точностью до 0,01 ч**. Строгое равенство ставить нельзя: разбивка
  квантуется до сотых часа, а часы дня могут нести больше знаков (замер на проде дал
  максимум расхождения 0,0033 ч — 12 секунд). Объектные строки дополняют табель, а не
  заменяют его.
- `mode` — как считался человек: `skud` (по фактическим проходам), `object` (одна
  строка на закреплённый объект), `current_activity` (одна строка «Текущая
  деятельность»).
- `object_id: null` бывает у «Текущей деятельности» и у объекта «Не определён»
  (проход не смаплен) — различать по `object_name`.
  Часы в «Не определён» **не выбрасывать**: иначе итог по объектам не сойдётся
  с табелем.
- `objects: []` — у сотрудника нет дней с положительными часами. Не ошибка.
- Разбивка есть не у всех отделов: где объектной активности нет, всё придёт одной
  строкой «Не определён» либо `objects` будет пуст.

**Два отказа, при которых ACK отправлять нельзя:**

| Код | Что значит | Что делать |
|---|---|---|
| `409 OBJECT_BREAKDOWN_NOT_AVAILABLE` | Редакция старше внедрения метода | Пропустить подачу, повторить в следующем цикле |
| `409 INVALID_EXPORT_MODE_CONFIG` | У части сотрудников повреждён режим табелирования, их часы недостоверны. В поле `employees` — список `employee_id` с причиной | Сообщить администратору ФОТ. Само не исправится: после починки настройки табель нужно открыть и закрыть заново |

Если отправить ACK в этих случаях, подача уйдёт из очереди, а объектные строки в
документ так и не попадут — и никто об этом не узнает.

Отдаётся руководитель **того отдела, к которому сотрудник относится в этом табеле**.
Руководители родительских отделов, «ответственные согласующие» и подбор по должности не

#### `resolution_status`

| Значение | Смысл | Что делать |
|---|---|---|
| `resolved` | ровно один пригодный руководитель | использовать |
| `multiple` | назначено несколько | **выбирать первого нельзя** — решать своим правилом либо оставить поле пустым |
| `not_configured` | отдел известен, руководитель не назначен | штатная ситуация, поле пустое |
| `department_unknown` | отдел определить не удалось | проблема данных, сообщить администратору ФОТ |
| `invalid_configuration` | назначения есть, но ни одного пригодного (уволен, архивен, нет в справочнике) | запись остаётся в массиве, но автоматически использовать её нельзя |

**`managers: []` — это норма, а не ошибка.** На момент внедрения руководитель не назначен
ни у «ЛИНИЯ», ни у «ЛИНИЯ-Общестрой», и по ним всегда придёт `not_configured`.

#### Прочие правила

- **Сопоставлять руководителя только по `employee_id`** (реквизит `ID_FOT`). ФИО — исключительно
  для отображения: полные однофамильцы существуют.
- `resolution_basis` показывает, откуда взят отдел: `approval_department` (из подачи отдела)
  либо `employee_assignment_period` (из истории назначений за период подачи).
- Проблемные записи не скрываются, а помечаются `data_quality_issues`:
  `manager_dismissed`, `manager_archived`, `manager_metadata_missing`,
  `manager_name_looks_test` — у руководителя; `department_changed_during_period`
  (внутри периода был перевод, взят отдел на конец), `department_history_missing`
  (отдел взят из карточки, а не из истории), `department_unknown` — у сотрудника.
- `snapshot_source`: `materialize` — состояние на момент **создания редакции**;
  `backfill_current_state` — состояние на момент дозаполнения старых редакций, то есть
  заведомо позже закрытия табеля. Истории назначений руководителей в ФОТ нет вовсе,
  поэтому «руководитель на даты табеля» не гарантируется ни в одном из случаев.
- Смена руководителя в ФОТ **не меняет уже закрытую редакцию**. Чтобы правка попала в 1С,
  табель открывают и закрывают заново — появится новая `revision`.

#### Отказ, при котором ACK слать нельзя

`409 MANAGERS_NOT_AVAILABLE` — редакция старше внедрения метода и не дозаполнена.
Пропустить подачу, повторить в следующем цикле. Прочие коды — те же, что у табеля.

### Шаг 3. Записать документ в 1С

Документ ищется по `approval_id` и **обновляется**, а не создаётся заново.
`approval_id` — постоянный идентификатор табеля, он не меняется между редакциями.

Вместе с часами по дням записываются объектные строки из шага 2а и руководители из
шага 2б; сохраняются `objects_content_hash` и `managers_content_hash` — по ним на
следующем цикле видно, что именно изменилось.

**Порядок обязателен.** Сначала успешно получить все три ответа — табель, объекты и
руководителей, — и только потом писать документ и отправлять ACK. Любой `409` на любом
из трёх шагов означает «пропустить подачу целиком, ACK не отправлять»: иначе документ
уйдёт неполным, а подача исчезнет из очереди, и никто об этом не узнает.

### Шаг 4. Подтвердить приём

```
POST /api/public/v1/timesheets/855/ack
Content-Type: application/json

{ "revision": 2, "document_ref": "ТАБ-000123" }
```

Отправляется **только после успешной записи документа**. После этого табель
переходит в `exported`, и в ФОТ у него появляется зелёная отметка.

`content_hash`, `employees_count` и `total_hours` сервер берёт из своей версии —
передавать их не нужно.

## 7a. Подтверждение — не опция

**Шаг 4 обязателен.** Пока 1С не подтвердила редакцию через `POST .../ack`, подача
остаётся в состоянии `not_exported` и возвращается в выборку `needs_export=true`
**в каждом цикле опроса, бесконечно**. Ошибки при этом не будет: ФОТ просто считает,
что документ в 1С так и не появился.

Отсюда два правила внедрения:

- подтверждать **сразу после** того, как документ в 1С записан и проведён;
- при обрыве связи между записью документа и подтверждением — **повторить ACK**.
  Он идемпотентен: повторное подтверждение той же редакции не создаёт вторую запись
  и возвращает исходное время приёма. Если неизвестно, прошёл ли ACK, — повторите,
  это безопасно.

Обратное тоже верно: **не подтверждайте то, что не провели**. ACK означает «редакция
принята и учтена в 1С». Подтверждение без документа уберёт табель из очереди, и
никто об этом не узнает.

## 8. revision и хэши

- `revision` — номер официальной редакции, растёт с каждой новой версией.
- `content_hash` — md5 содержимого табеля (часы по дням, состав, итоги).
- `objects_content_hash` — md5 объектной разбивки, приходит в ответе шага 2а.
- `managers_content_hash` — md5 руководителей, приходит в ответе шага 2б.

**Сверять нужно ВСЕ ТРИ хэша.** Совпадения одного `content_hash` недостаточно: при
неизменных часах могла измениться объектная разбивка (часы дня переставили с одного
объекта на другой, итог прежний) или руководитель отдела. Любое такое изменение даёт
новую `revision`, и подача штатно возвращается в `needs_export`.

Правило:

- все три хэша совпали с принятыми — документ можно не перепроводить;
- разошёлся любой из трёх — перечитать и перепровести.

В обоих случаях **ACK новой `revision` отправить обязательно** — иначе табель
навсегда останется в состоянии `stale` и будет вечно возвращаться в `needs_export`.

## 9. Ошибки и повторы

| Ответ | Причина | Что делать |
|---|---|---|
| `409 TIMESHEET_REBUILD_PENDING` | Идёт аварийная пересборка версии (ручное восстановление данных). Редкий случай | Пропустить, повторить в следующем цикле (обычно ~минута) |
| `409 TIMESHEET_VERSION_INCOMPLETE` | Версию собрать не удалось: состав подачи неполон. Требует вмешательства администратора ФОТ | Пропустить, сообщить администратору, если повторяется |
| `409 TIMESHEET_UNLOCKED` | **Больше не возвращается.** Оставлен в перечне кодов для совместимости: открытый табель теперь отдаётся как обычно | Обработчик можно сохранить, срабатывать не будет |
| `409 TIMESHEET_NOT_APPROVED` | Подача больше не утверждена | Пропустить |
| `409 OBJECT_BREAKDOWN_NOT_AVAILABLE` | Объектная разбивка редакции не сформирована (шаг 2а) | Пропустить, **ACK не слать** |
| `409 INVALID_EXPORT_MODE_CONFIG` | Повреждён режим табелирования у части сотрудников (шаг 2а) | **ACK не слать**, сообщить администратору ФОТ |
| `409 MANAGERS_NOT_AVAILABLE` | Руководители редакции не сформированы (шаг 2б) | Пропустить, **ACK не слать** |
| `409 VERSION_NOT_AVAILABLE` | Версия ещё не сформирована | Пропустить, повторить позже |
| `409 REVISION_MISMATCH` | Между загрузкой и ACK появилась новая редакция | Перечитать табель, обработать заново, подтвердить новую `revision` |
| `429` | Превышен лимит запросов ключа | Выдержать окно (по умолчанию 60 запросов в минуту) |
| `401` | Токен неверен, отозван или просрочен | Остановить обмен, обратиться к администратору ФОТ |
| `403` | Ключу не открыт доступ или не включено подтверждение | Обратиться к администратору ФОТ |

**Восстановление после сбоя связи.** ACK идемпотентен: повторное подтверждение той же
`revision` возвращает исходный `acked_at` и не создаёт вторую запись. Если связь
оборвалась после записи документа, но до ACK — просто повторите ACK. Если
неизвестно, прошёл ли ACK, повторите его: это безопасно.

```bsl
    КонецЕсли;

    КонецЕсли;

    Результат = Новый Структура("Код, Тело");

    Курсор = "";

    Пока Истина Цикл

        Путь = "timesheets?month=" + Месяц + "&needs_export=true&limit=100";
        Если ЗначениеЗаполнено(Курсор) Тогда
            Путь = Путь + "&cursor=" + Курсор;
        КонецЕсли;

        Список = ЗапросТабелей("GET", Путь);
        Если Список.Код <> 200 Тогда
            ЗаписьЖурналаРегистрации("ФОТ.Табели", УровеньЖурналаРегистрации.Ошибка,
                , , "Список: код " + Список.Код);
            Прервать;
        КонецЕсли;

        Для Каждого Строка Из Список.Тело["data"] Цикл

            // Версия ещё не сформирована — вернёмся к этому табелю позже.
            Если Не Строка["version_available"] Тогда
                Продолжить;
            КонецЕсли;

            ИдентификаторТабеля = Строка["approval_id"];
            Ревизия = Строка["revision"];

            Табель = ЗапросТабелей("GET", "timesheets/" + Формат(ИдентификаторТабеля, "ЧГ=0"));

            // 409 — версия ещё не готова или идёт аварийная пересборка: до следующего цикла.
            Если Табель.Код = 409 Тогда
                Продолжить;
            КонецЕсли;
            Если Табель.Код <> 200 Тогда
                Продолжить;
            КонецЕсли;

            // Часы по объектам — ТОЙ ЖЕ редакции, что и табель.
            Объекты = ЗапросТабелей("GET", "timesheets/" + Формат(ИдентификаторТабеля, "ЧГ=0")
                + "/objects?revision=" + Формат(Табель.Тело["revision"], "ЧГ=0"));

            // 409 здесь — OBJECT_BREAKDOWN_NOT_AVAILABLE или INVALID_EXPORT_MODE_CONFIG.
            // ACK слать НЕЛЬЗЯ: подача уйдёт из очереди без объектных строк.
            Если Объекты.Код <> 200 Тогда
                Если Объекты.Код = 409 И Объекты.Тело["code"] = "INVALID_EXPORT_MODE_CONFIG" Тогда
                    ЗаписьЖурналаРегистрации("ФОТ.Табели", УровеньЖурналаРегистрации.Ошибка,
                        , , "Табель " + ИдентификаторТабеля + ": повреждён режим табелирования, "
                            + "сообщите администратору ФОТ");
                КонецЕсли;
                Продолжить;
            КонецЕсли;

            // Руководители отдела — той же редакции.
            Руководители = ЗапросТабелей("GET", "timesheets/" + Формат(ИдентификаторТабеля, "ЧГ=0")
                + "/managers?revision=" + Формат(Табель.Тело["revision"], "ЧГ=0"));

            // 409 здесь — MANAGERS_NOT_AVAILABLE. ACK слать НЕЛЬЗЯ.
            Если Руководители.Код <> 200 Тогда
                Продолжить;
            КонецЕсли;

            // Все три ответа получены — только теперь пишем документ.
            Успешно = ЗаписатьДокументТабеля(Табель.Тело, Объекты.Тело, Руководители.Тело);
            Если Не Успешно Тогда
                Продолжить;   // ACK не отправляем — заберём в следующем цикле
            КонецЕсли;

            ТелоACK = Новый Структура;
            ТелоACK.Вставить("revision", Табель.Тело["revision"]);
            ТелоACK.Вставить("document_ref", "ТАБ-" + Формат(ИдентификаторТабеля, "ЧГ=0"));

                "timesheets/" + Формат(ИдентификаторТабеля, "ЧГ=0") + "/ack", ТелоACK);

            // Пока писали документ, табель успели закрыть заново — появилась новая редакция.
            Если Подтверждение.Код = 409 Тогда
                ЗаписьЖурналаРегистрации("ФОТ.Табели", УровеньЖурналаРегистрации.Предупреждение,
                    , , "Табель " + ИдентификаторТабеля + " изменился, заберём заново");
            КонецЕсли;

        КонецЦикла;

        Курсор = Список.Тело["next_cursor"];
        Если Курсор = Неопределено Тогда
            Прервать;
        КонецЕсли;

    КонецЦикла;

КонецПроцедуры
```

## 11. Диагностика

- **Журнал обращений.** Каждый запрос к API пишется в ФОТ: админка → «API-доступ» →
  ключ → «Лог запросов». Видны время, метод, код ответа, длительность и текст ошибки.
- **Сверка содержимого.** Если возникло подозрение, что в 1С попали не те данные,
  сравните `content_hash` документа с `content_hash` текущей версии
  (`GET /timesheets/{approval_id}`). Разошлись — значит в 1С лежит старая редакция,
  её нужно перечитать и подтвердить заново.
- **Табель «завис» в `needs_export`.** Почти всегда причина одна: документ записан,
  а ACK не отправлен. Отправьте ACK текущей `revision`.
- **Состояние в интерфейсе ФОТ.** В разделах «Табели HR» и «Согласования» у каждого
  табеля показан статус выгрузки: выгружен / изменён после выгрузки / не выгружен,
  с датой подтверждения и номером документа.
